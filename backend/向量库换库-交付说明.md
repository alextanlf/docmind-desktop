# chromadb → sqlite-vec 换库交付说明

> 2026-10-06 完成。全部结论来自本机实测，非估算。

## 一、结果

| 指标 | 换库前 | 换库后 |
|---|---|---|
| 后端 runtime | 576M | **399M** |
| site-packages 包数 | 200 | **91** |
| 向量库及依赖 | 134M | **188K** |
| 全量测试 | 928 passed | **930 passed** |

省下 **177M**，且检索语义与原实现完全一致（`query` / `where` 过滤结果逐条比对相同）。

## 二、为什么选 sqlite-vec

三个候选全部实测可安装（阿里云镜像，直连 pypi.org 超时）：

| 库 | 新增体积 | 传递依赖 | 结论 |
|---|---|---|---|
| **sqlite-vec 0.1.9** | **188K** | **0 个** | 选定 |
| hnswlib 0.8.0 | ~5M | 0 个 | 当前规模无必要 |
| faiss / lancedb / qdrant | 更大 | 多 | 过度设计 |

sqlite-vec 的决定性优势是**零传递依赖** —— 只需一个 wheel，不引入 C 编译链，
沙箱与离线环境友好。对比 chromadb 的 134M（其中 kubernetes 44M + grpc 40M
纯属集群形态的包袱，本地嵌入式永远用不到）。

**性能实测**（1024 维 float32，cosine，Apple Silicon）：

| 向量数 | 写入 | top-3 查询 |
|---|---|---|
| 1,000 | 421 ms | 1.47 ms |
| 5,000 | 1,941 ms | 6.02 ms |
| 20,000 | 7,813 ms | 23.18 ms |

桌面端规模（1000 篇文档 × 20 块 = 2 万条）查询 23ms，远低于 LLM 网络往返。

## 二·五、为什么不用纯 numpy 扫描

numpy 本来就在（`onnx_embedding.py:32` 已 import），且**确实快一个数量级**。
同条件实测（1024 维 float32 cosine，runtime 解释器）：

| 向量数 | sqlite-vec | 内存 numpy | 差距 | 内存索引 | sqlite 磁盘 |
|---|---|---|---|---|---|
| 10,000 | 10.8 ms | **0.64 ms** | 17× | 39 MB | 41 MB |
| 50,000 | 53 ms | **3.3 ms** | 16× | **195 MB** | 201 MB |

选 sqlite-vec 就是**主动接受这 17× 换内存**：

| | 纯 numpy | sqlite-vec |
|---|---|---|
| 查询 | 0.64 ms | 10.8 ms |
| 进程常驻内存 | 39~781 MB（随规模线性涨） | **~0**（向量留磁盘，按需读） |
| 持久化 | 要自己管 `.npy` 文件、并发写、崩溃恢复 | SQLite 事务，WAL |
| 维度变更 | 重建数组即可 | 需重建表（已拦截并提示） |
| 增量写 | 要重算整个矩阵或分段管理 | 单条 upsert |

**判断依据**：当前规模（2 万条）两者绝对值都远低于 LLM 网络往返，sqlite-vec 的
23ms 用户无感；而 195 MB 常驻内存对一个 Electron 桌面后端是实打实的负担
（bge-m3 ONNX 已占数百 MB）。桌面端索引到 20 万条时内存索引要 781 MB，
那时该重新评估 —— 但那不是现在的场景。

**结论**：这是一个「用可忽略的绝对延迟换内存与持久化健壮性」的选择，
不是「numpy 更快为什么不用」的错误。真正的取舍点是内存，不是速度。

## 三、关键设计决策

### 1. 距离度量必须显式写 cosine

sqlite-vec 的 `vec0` **默认 L2**，与 chromadb 的 `hnsw:space=cosine` 语义不同。
不写 `distance_metric=cosine` 检索结果会变。cosine 下 `1 - distance` 恰好
等于余弦相似度，与旧实现同口径，因此 `memory/retriever.py` 的 0.65 阈值无需重调。

### 2. 表名必须加双引号（踩坑两次）

生产里 `repository_id` 是 UUID（`0fba5e94-aaf2-46e5-...`），而 `collection_name()`
的既有行为是只把非 `[A-Za-z0-9_-]` 替换成下划线 —— **连字符被保留**。于是表名
形如 `repo_0fba5e94-aaf2-...`，未加引号时 SQLite 把它当减法：

```
sqlite3.OperationalError: near "-": syntax error
```

正确做法是 `_qi()` 给所有表名包双引号，而不是试图禁止连字符
（测试锁定了 `repo-1 → repo_repo-1` 这个映射行为，不能改）。

**这个 bug 造成 27 个测试失败**，而错误被 `imports/service.py:646` 的
`except Exception` 吞成「写入文档索引失败」，一度难以定位。

### 3. 维度由实际数据决定，不是全局常量

`vec0` 把维度固化在表定义里（运行期无法 ALTER）。最初实现用
`VectorStoreSettings.dimension`（默认 1024）建表，结果 28 个测试失败 ——
测试普遍用 2/3/8 维构造小样本，这是合理用法。

改为 `_dimension_of(embeddings)` 从实际数据取维度，并保留配置项作为生产默认值。
查询时用 `_stored_dimension()` 读回实际维度做校验，换嵌入模型后给出
「需要重建索引」而不是裸 sqlite 错误。

### 3.5 批量删除必须分批（`too many SQL variables`）

`WHERE id IN (?,?,?,...)` 会按条数展开绑定变量，撞上 SQLite 的
`SQLITE_MAX_VARIABLE_NUMBER`（实测 `getlimit` 确认 = **32766**）。
5 万条批量写入时直接报 `sqlite3.OperationalError: too many SQL variables`。

修法：`_batched(items, 1000)` 分批。三处都要改 ——
`_write` 的两条 DELETE、`_delete_ids`、`_search` 的元数据回表。
回归测试用 33,000 条（刚越过上限，2 维以控制耗时）。

这个 bug 是做「纯 numpy vs sqlite-vec」对比测 5 万条时**顺带发现的**，
不在 930 个测试的覆盖范围内（测试用的小样本远低于上限）。

### 4. 元数据走独立表 + 候选集放大
`vec0` 的 metadata 列不支持任意键值，分区键会改变 ANN 遍历顺序。改为：
向量表只管 `id + embedding`，正文与 metadata 走普通表，查询后回表。

`where` 过滤用「放大候选集（10×，上限 512）+ 回表筛」。只实现等值条件 ——
实际用到的只有 `section_path` 和 `repository_id` 两种，范围/IN/AND-OR 没有
调用方需要，写了就是没人验证的死代码。

### 5. collection 用独立表而非 partition key

`delete_collection` 需要整体删除某仓库的全部向量。共享表 + partition key 做不到
干净删除，只能扫行，得不偿失。

### 4.5 过滤必须下推到 SQL（🔴 修掉一个静默漏召回）

初版实现是「按相似度取 `top_k×10` 条 → 在 Python 里筛」。**这是错的**：

```
100 条里 2 条匹配 doc_id='d1'，top_k=3（窗口 30）→ 返回 0 条，无任何报错
```

低选择性过滤时，匹配项一旦排在窗口之外就永远取不到。而
`core/retrieval.py:235` 的概览块注入正是这个形态：

```python
where={"section_path": OVERVIEW_SECTION_PATH}
```

概览块在一份文档里只有一块，正文块动辄几十上百块 —— 选择率天然极低。
**这意味着全局型查询的召回会悄悄少一块，且没有任何报错。** 而"overview chunk
注入优于 reranker"正是本项目的核心结论之一。

修法：把 `_METADATA_KEYS` 全部建成 vec0 的 text 列，`MATCH` 查询带
`AND "col" = ?`，由扩展在 ANN 遍历时筛选。`fetch` 不再放大，`k` 就是真实行数，
语义与选择率无关。实测 200 条中唯一匹配项（相似度 0.1，99 条干扰项相似度 0.9）
可正确取回。

配套的 `_filter_value()` 有两个必须注意的点：
- **bool 要特判**：`str(True) == "True"` 而 JSON 是 `true`，两边规则必须一致
- **缺失写空串不能写 `None`**：vec0 的 metadata 列不接受 NULL

### 4.6 vec0 的三个语法坑（都与普通 SQLite 不同）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 列名不能加引号 | `vec0 constructor error: Could not parse '"doc_id" text'` | 裸写（列名来自模块常量，安全） |
| metadata 列不接受 NULL | `Expected text for TEXT metadata column doc_id, received NULL` | 显式给空串 |
| 默认距离是 L2 | 检索结果与 chromadb 不一致 | 显式 `distance_metric=cosine` |

## 四、旧数据处理

本机 `vectorstore/chroma.sqlite3` 实测 **0 条向量**（`segments=0`/`embeddings=0`），
因此**无需迁移**。

代码层面：`_retire_legacy_chroma()` 在启动时把旧文件改名为 `chroma.sqlite3.legacy`。
- **不删** —— 删用户数据不该由代码在启动时顺手做掉
- 幂等 —— 已改名的不会重复处理
- 失败静默 —— 文件被占用/权限不足不影响新库工作

**真实用户若已有非空索引，需要重建**（两种格式的向量无法搬迁）。这是本次换库
唯一的用户侧代价，触发条件是「之前用过 DocMind 且导入过文档」。

## 五、构建期防回归

`build-backend-runtime.sh` 6.1 节的探针覆盖：建集合 → 写入 → 无过滤查询 →
where 过滤 → 记忆索引三方法 → 维度不匹配拦截 → 删除 → 删集合 → 查不存在的集合，
且用 **UUID 作为仓库名**（覆盖生产的真实形态）。

**探针用 `-I` 隔离模式 + 断言 `sqlite_vec.__file__.startswith(sys.prefix)`。**
这不是形式主义：上一轮 chromadb 剪枝的探针就是因为解释器会从 runtime 之外
兜底加载真包，导致「删掉必需包后探针仍返回 OK」，静默失效。

探针有效性已用 mutation test 验证：

| 变异 | 探针反应 |
|---|---|
| 隐藏 `sqlite_vec/` | `ModuleNotFoundError` ✓ |
| 隐藏 `vec0.dylib` | `OperationalError: not authorized` ✓ |

**判据：验证工具本身必须先证明能抓到失败。**

## 七、代码审查：修掉一个静默漏召回

换库完成后做了一轮逐行审查 + 针对性实测，找到 1 个严重 bug 并修复。
最终 **935 tests passed**，构建 399M。

### 🔴 where 过滤静默漏召回（已修）

初版「取 top_k×10 条再在 Python 里筛」在低选择性过滤下会漏召回且不报错，
详见 4.5 节。影响面是概览块注入 —— 全局型查询的召回会少一块。

回归用例（4 个）：
- `test_vector_store_where_filter_does_not_lose_sparse_matches` — 100 条中 2 条匹配
- `test_vector_store_where_filter_finds_match_at_the_bottom_ranking` — 匹配项相似度最低
- `test_vector_store_where_filter_handles_int_bool_and_zero_values`
- `test_vector_store_concurrent_writes_and_reads` — 6 写 + 4 读并发

构建探针也加了对应的极端场景。

### 审查过且确认没问题的维度

| 维度 | 结论 |
|---|---|
| 并发 | 10 线程写 + 5 读，无错误，集合互不干扰（RLock 足够） |
| 事务 | 维度校验在 DELETE **之前** → 失败时旧数据完好 |
| 崩溃恢复 | 重开连接数据完好（WAL） |
| 孤儿向量 | 元数据丢失时跳过脏命中，不返回空 metadata |
| top_k 边界 | `0`/`-1` → 空；超量 → 返回实际条数 |
| SQL 注入 | `a"b` / `a'b` / `a;b` / `a--b` / `../../etc` 全被替换或引号隔离 |
| 类型一致性 | int/float/bool/`0`（falsy 但有效）都正确；`'3'` 不匹配 `3`（正确） |

### 一次误判的记录

我一度判定「写入失败没回滚、`x,y` 被部分写入」。**这是误判** ——
测试用例里的 `{'doc_id': Bad()}` 被 `_metadata()` 白名单过滤掉，写入其实
**成功了**。误判原因：只看查询结果，没确认是否真的抛了异常。

### 探针自身的教训

第一版探针**假通过**了变异测试：场景里干扰项与匹配项相似度相同，落在放大窗口内，
注入 bug 后探针仍返回 OK。改成「唯一匹配项相似度 0.1 < 99 条干扰项 0.9」后
才真正抓到（`AssertionError: []`）。

**判据：探针的场景必须让 bug 的触发条件成立，不能只覆盖正常路径。**

## 八、遗留与建议

1. **用户侧需重建索引**（如有非空旧索引）。可在设置里加「重建索引」入口，
   复用 `embedding_rebuild` 表。
2. **`playwright` 146M 仍是最大冗余**（128M 是 Node 中间层，Chromium 本体
   反而不在安装包里）。这是独立议题，本次未动。
3. **写入吞吐 2 万条 7.8s** 偏慢（JSON 序列化 + 逐条 INSERT）。当前是
   文档导入时一次性调用，用户无感；若将来批量导入场景变多，可改用
   `executemany` 批量化或换二进制 blob 存储。
4. `google`（protobuf 1.7M）与 `opentelemetry` 仍在 runtime 里 —— 它们来自
   fastapi/starlette 自身，与 chromadb 无关，不应剪。
