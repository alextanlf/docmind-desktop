# 直接用磁盘上的原件：链接模型（B 形态 + 目录批次）

> 2026-10-12 · 基于源码核对与本机数据实测。设计阶段：第七节的阶段 1 之后才动代码。
> 前情见 `docs/文档存储优化方案.md`（L0 暂存清扫、L1 原件分层保留已落地）。

## 一、目标与必须守住的三条不变量

**目标**：导入时直接读用户磁盘上的文件，只把**转换后的 markdown** 复制进应用。原件（PDF、docx、
`.pages`…）留在原地，长期绑定，并且当它被改动、被移动、被删除时应用能说清发生了什么。

三条不变量，任何实现都不许破：

1. **渲染层不能指名任意文件。** 今天主进程只把"用户在对话框里选中的那个文件"复制进暂存，
   后端的 `StagedFileStore` 又强制 `value` 是规范 UUID（`_validated_staged_path`），
   IPC 面是一份固定的 93 个 channel 的清单、没有通用透传 —— 所以渲染层**没有**任何办法让
   后端去读一个它自己挑的路径。插件 UI 就是渲染层代码，这条性质必须留着。
2. **不弄丢用户的文件。** 应用只读原件，永不写、永不删。删除文档只允许动
   `documents/<id>/` 这一棵树。
3. **一致性保证不降级。** 目录批次现在的语义是"你确认的内容 == 真正导入的内容"
   （manifest 的 sha256 校验，变了就 `BATCH_SOURCE_CHANGED`）。就地读**不放弃**这条保证，
   见第五节。

## 二、为什么不是"把字节流传给后端"

看起来最省事的做法是：主进程读原文件，把字节流发给后端解析，后端连路径都不用知道。
走不通，理由是硬的：

- `max_request_body_bytes` 默认 **10 MB**（`config.py`），而单个文件上限 **100 MB**
  （`pdf_max_bytes`）。一次导入一个 80 MB 的 PDF，请求体就超了。
- 即使抬掉这个限制，二进制过 IPC 走的是 base64（本仓库既有约定，见
  `DocumentOriginalChunkSchema` 的注释），体积 +33%，而且要在内存里整体持有。
- 抬限制等于同时抬掉所有接口的保护，代价远超收益。

所以**路径必须跨到后端**。问题只剩"怎么跨得安全"。

## 三、信任模型：路径 = 能力（capability）

主进程生成 token，后端只读 token 对得上的路径：

```
token = base64url(HMAC_SHA256(session_token, domain + ":" + path))
domain ∈ { "linked-file", "linked-directory" }
```

- `session_token` 是主进程生成、经环境变量注入后端的那个（`backend-manager.ts:122`），
  两边都有，渲染层拿不到。
- **签的是路径字符串的原始 UTF-8 字节，两边都不做规范化。** 这是刻意的：TS 的
  `path.resolve`/Python 的 `Path.resolve` 在符号链接、大小写、Unicode 归一化（macOS 的
  HFS+/APFS 会做 NFD）上不一致，跨语言各自规范化必然出现"签名对不上"或更糟——
  "两个不同的字符串被规范成同一个路径"。签名与校验都用同一个不可变字符串，
  规范化只发生在后端落地读取之前，且只用于**安全检查**（是否普通文件、是否在授权目录内）。
- 两个 domain 分开，是为了让"授权一个目录"不能被当成"授权某个文件路径"来用。
- **不做过期**：token 的生命周期等于路径授权本身（B 形态就是要长期绑定）。泄露一个 token
  的后果被限制在那一个路径上。

后端校验通过后，才允许 `open()`。校验失败一律 `SOURCE_UNSUPPORTED`（400、不可重试），
且**不透露路径是否存在** —— 否则它成了一个"任意路径存在性探测器"。

## 四、数据模型

`raw_path` 的语义收窄为「**我们自己存的**原件副本」（历史字段，已存文档仍在用）。
新增两列，指向用户磁盘：

| 列 | 类型 | 含义 |
|---|---|---|
| `source_path` | `Text NULL` | 用户磁盘上的原件绝对路径（**永不出后端**） |
| `original_revision` | `String(128) NULL` | 导入那一刻原件的 `mtime_ns:size`，用于变更检测 |

- 迁移 `0026_linked_originals`。
- `raw_path` 与 `source_path` 互斥的约定由代码守：写了一个就不写另一个。
- **路径不进 wire model**：`DocumentSummary` 不含 `raw_path`/`markdown_path`（现在如此），
  新列同样不进。渲染层只拿得到"原件可用/已变更/已丢失"这个状态。
- 已有文档**不迁移**：它们继续用自己那份副本。理由见第八节。

原件位置只有一个解析入口：

```python
def original_path(document) -> Path | None:
    return Path(document.source_path or document.raw_path or "") or None
```

`_original_info()` 与 `GET /raw` 都改走它 —— 它们在 L1 里就被定义成"原件视图可用的字节"，
换成用户的文件不需要改一处逻辑（Range 由 Starlette 的 `FileResponse` 负责）。

## 五、目录批次就地读：一致性保证怎么保住

今天的目录批次是：主进程**逐个复制**文件进 `staging/collections/<id>/items/<stagedId>`，
同时算出 sha256 写进 manifest；后端校验 manifest，再从暂存读。

就地读的版本，复制这一步换成**扫描**：

1. 主进程遍历目录，对每个文件**流式算 sha256**（读一遍，不落盘），写 manifest：
   `relativePath` + `sizeBytes` + `sha256` + `mediaType`，外加授权签名覆盖的 `rootPath`。
2. 用户确认导入；后端按 `rootPath/relativePath` 读文件，**读的时候再算一次 sha256 并比对**。
   不一致 → 与今天完全相同的 `BATCH_SOURCE_CHANGED`（"文件在确认之后被改过"）。
3. 路径包含性检查照旧（`PurePosixPath` 拒绝 `..`、拒绝逃出 root 的符号链接）——
   这一层与今天 `staging_manifest` 里已有的校验同一份逻辑，不新写第二份。

**代价**：每个文件多读一遍（扫描时哈希一次、导入时读一次），换来零磁盘重复。
**收益**：一次导入一个 500 MB 的资料目录，不再需要同等大小的暂存空间。

> 一个必须写进注释的取舍：扫描时算 sha256 会让"选目录"这个动作变慢（原来是边复制边算，
> 复制与哈希同一次 I/O）。选了 300 个文件就要读 300 遍。所以扫描必须放后台、带进度，
> 不能像今天这样同步阻塞对话框 —— 这是这个阶段最容易低估的工作量。

## 六、原件状态机

| 状态 | 触发 | 前端表现 |
|---|---|---|
| `available` | 路径存在且 `mtime_ns:size` 与 `original_revision` 相同 | 「原文」标签正常 |
| `changed` | 路径存在但 revision 不同 | 「原文」可看，但带一条提示：「原件已更新，要重新转换吗？」 |
| `missing` | `stat` 失败 | 「原文」标签保留但禁用，提示「原件已移动或删除」+「重新定位」 |
| `none` | 没有 `source_path` 也没有 `raw_path`（本地新建的文档） | 不显示「原文」 |

- 状态由**读取时**算（`GET /api/documents/{id}` 里 `stat` 一次），不落库、不后台轮询。
  `stat` 是微秒级，比在数据库里维护一个必然过期的"状态列"诚实。
- `DocumentDetail.original_state` 是新字段；「无原件」与「原件丢了」在接口上必须可区分，
  否则前端只能显示"没有原文"，用户不知道是自己没导入原件还是文件被挪走了。
- **重新定位**：`POST /api/documents/{id}/original`，body 是新的 `{path, token}`
  （同样是主进程签的）。语义只改绑定，不自动重新转换 —— 转换是一次会动索引与版本的重操作，
  由用户显式点「重新转换」触发。
- **重新转换**：复用已有的更新流水线（读原件 → `parse` → `_index` → `_persist_content`，
  带版本快照与回滚补偿）。它已经处理了向量替换失败、取消、崩溃恢复，不要另写一条。

## 七、平台约束（会真实遇到）

- **macOS TCC**：非沙盒应用读 `~/Documents`、`~/Desktop`、`~/Downloads` 会触发一次系统授权
  弹窗。用户在文件对话框里选过文件之后，授权作用于整个应用进程树，所以**之后的读取不再弹**。
  但如果用户从没通过对话框授权过（例如文档是在另一台机器上导入的，`source_path` 指向
  本机同名目录），第一次读原件时才会弹 —— 这个弹窗由系统管理，应用无法预判，
  所以「原件暂时读不到」必须是一个**正常状态**而不是错误。
- **不需要 security-scoped bookmark**：`electron-builder.config.js` 里
  `hardenedRuntime: false`、无 entitlements、非沙盒，路径在重启后依然可读。
  如果将来开启沙盒，这一节必须重做（bookmark 与路径签名是两套东西）。
- Windows/Linux 无对应机制；但两个平台都会遇到"盘符变了/挂载点没了"（移动硬盘、网络盘），
  与 `missing` 走同一条路径。

## 八、明确不做的事

1. **不迁移已有副本**：已有文档继续读自己那份 `raw.bin`。迁移需要用户重新指定文件，
   而"重新指定"对用户来说是纯负担；等到有人真的需要（比如想省那 1.1 MB）再提供
   按文档的「转为链接」。
2. **不把路径交给渲染层**：包括「在访达中显示」这类按钮。要做就走 IPC 让主进程用
   `shell.showItemInFolder`，而不是把路径发到渲染层再传回来。
3. **不做后台文件监视**：状态在读取时算。监视几千个文件的目录要另算代价，
   而且用户改文件与应用是否知道之间不需要实时性。
4. **不做"书库目录"的独立概念**：授权发生在用户选文件/选目录的那一刻。
   "常驻书库 + 定时重扫"是另一个功能，本方案只保证路径授权是长期有效的。

| 阶段 | 内容 | 会红的测试 |
|---|---|---|
| **1** | 签名能力（TS + Python 各一份实现，互相钉住）、`linked_file` 单文件导入不落副本、`original_path` 统一解析、PDF 原件视图读用户的文件 | 伪造/篡改 token 被拒且不泄露路径是否存在；导入后 `documents/<id>/` 里没有 `raw.bin`；`/raw` 对链接原件仍支持 Range；文件被删后 `/raw` 返回 `DOCUMENT_ORIGINAL_MISSING` 而不是 500 |

## 十一、已落地：阶段 1 的后端一半

### 11.1 路径能力

`app/document/path_tokens.py` 与 `electron/main/path-tokens.ts` 各自实现 HMAC-SHA256，
两边共用同一组测试向量（token/路径/期望值逐个字节相同，路径里特意放了中文 ——
编码一旦按错，纯 ASCII 路径照样能通过）。任一边改了算法、消息构造或编码，
只有"共享向量"那条断言会红，其余几条（比大小、比 URL 安全性）都还是绿的 ——
这个形状本身说明向量确实钉住了跨语言契约，而不是在测各自实现的自洽。

### 11.2 只有主进程签得出名字

`LinkedFileStore.load` 的第一件事就是验签，**在任何文件系统访问之前**。
因此：

- 拿不到签名的人，问什么都是同一句 `SOURCE_UNSUPPORTED`（400、不可重试）——
  不会因为"路径存在"与"不存在"给出不同回答。这一点单独立了一条用例。
- 签名有效但文件读不到时，才允许说"原件不可读"。这是有意的：签名等价于
  "用户真的选过这个路径"，此时更具体的报错不构成泄露，而用户需要它。

这条边界一开始写错了（两种情况都给不同文案），是测试逼出来的修正，记在这里。

### 11.3 枚举只声明一次

加 `linked_file` 时真的踩到了 AGENTS.md 里那句话描述的情形：`SourceRef` 与
`SourcePreview` 各声明了一份 `Literal["url","staged_file"]`，只改一处就抛运行时
`ValidationError`（不是测试失败）。改成在 `schemas/imports.py` 里声明一次
`SOURCE_KINDS`，并由 `contracts.test.ts` **去读那份 Python 源码**逐字比对 TS 的
`SOURCE_KINDS`（与 `MODEL_PRESET_IDS` 那组同一套做法）。变异验证：把 TS 那份
去掉 `linked_file`，只有这条断言红。

### 11.4 数据与读取路径

- 迁移 `0026_linked_originals`：`documents.source_path` + `documents.original_revision`
  （`mtime_ns:size`）。`test_migrations.py` 的列清单断言按预期变红过一次，已更新。
- `api/documents.py` 新增 `original_path()`，`_original_info()` 与 `GET /raw` 共用它：
  链接型优先，回落到历史 `raw_path`。**原件视图的代码几乎没改** —— 这两处本来就只关心
  "有没有字节可发"。
- `_persist_parsed_document`：链接型一律不写 `raw.bin`（哪怕格式是 `original_viewable`
  的 PDF），并顺手删掉同目录的历史副本；`source_path` 与 `original_revision` 落库。
- `path_token` 与 `name` 一样进 job metadata，重试重建 `SourceRef` 时一起取回 ——
  否则"应用重启导致中断"后的重试会在验签那一步失败。而 `_job_view` **刻意不回显**它：
  渲染层从头到尾见不到任何 token，这条不变量比省一个字段值钱。

### 11.6 阶段 1 的客户端接线（本轮完成）

- `StagedFileService.chooseAndLink(format)`：对话框 → 校验（扩展名、普通文件、大小上限，
  与暂存那条路同一套）→ **不写盘**，返回 `{kind, path, name, mediaType, sizeBytes}`。
- **能力登记**：服务里一个 `grantedPaths` 集合记住"对话框真的返回过的路径"。
  这是"路径 = 能力"里**能力的那一半** —— 光有签名不够：如果谁送来路径就签，
  签名就是一张空白支票，而送路径来的正是渲染层。只活在内存里，不需要跨重启，
  因为每个新路径都来自一次对话框。
- **签名位置**：`ipc-handlers.ts` 的 `withSignedPath`，只在 `imports:inspect` 与
  `imports:create` 两个处理器里补 `pathToken`。渲染层从头到尾不做也不需要签名。
- `index.ts` 把 `backend.start()` 返回的会话密钥传进服务；少了它，
  链接型导入会在签名那一步失败（有一条用例专门钉住这个"接线漏了"的情形）。
- `SourceStep` 改送 `linked_file`；`chooseSource` 的返回类型从 `StagedSource` 换成
  `LinkedSource`。

**顺带发现的一个测试漏洞**：`ipc-handlers.test.ts` 的依赖对象是 `as any` 强转的，
所以把 `chooseAndStage` 换成 `chooseAndLink` 时类型检查**不会**报错；而且当时没有一条
用例走过对话框 channel。已补 4 条（签名进入请求体、未授权路径被拒、create 路径也签、
非链接型不加签名），另在 `staged-files.test.ts` 补 6 条（不落副本、只签授权过的路径、
没有密钥时大声失败、校验与暂存一致、符号链接按用户选的路径处理）。

## 十二、已落地：阶段 2 的后端（原件状态 / 重新定位 / 重新转换）

### 12.1 状态是**读的时候算出来的**，不是存下来的

`api/documents.py` 的 `original_state(document)` 每次读文档时 `stat` 一下原件，四种取值：

| 状态 | 判据 | 用户看到什么 |
|---|---|---|
| `none` | 没有 `source_path` 也没有 `raw_path` | 没有「原文」标签 |
| `available` | 文件在，且 `mtime_ns:size` 等于记录的那一个 | 「原文」正常 |
| `changed` | 文件在，但对不上（**包括 revision 没记录**的情况） | 「原文」可看 + 提示「原件已更新，要重新转换吗？」 |
| `missing` | 文件 `stat` 不到 | 「原文」禁用 + 「原件已移动或删除」+「重新定位」 |

不落库的理由：数据库里存一个"状态列"，必然会在某一刻过期 —— 用户在我们两次检查之间移走了
文件，那一列就开始说谎。`stat` 是微秒级的，而"读的时候算"永远与磁盘一致。

**`missing` 与 `none` 必须分开**，这是这张表里唯一一个纯产品判断：合成一个值，前端就只能
显示"没有原文"，用户分不清是自己没导入原件，还是文件被挪走了 —— 而后者是他能修的。

### 12.2 重新定位**不更新** revision —— 这是它处理改名/移动的关键

`POST /api/documents/{id}/original {path, pathToken}` 只改绑定。绑定之后状态由"新文件的
`mtime_ns:size` 是否等于当初记录的那一个"算出来，于是：

- **文件被挪走/改名（内容没变）** → 状态自动回到 `available`，用户不会看到一个莫名其妙的
  "已更新"提示。`shutil.move` 保留 mtime，用例正是这么构造的。
- **换成另一个文件** → 状态是 `changed`，提示重新转换 —— 绑定成功了，但正文还是旧那一版
  转换出来的，这个提示是诚实的。

门与导入同一条：路径必须带主进程签名。否则"重新定位"就是绕开导入那道门、把任一篇文档指到
任意文件上的第二条路。签名用例里的假文件特意用了**受支持的扩展名**（`其实不是论文.pdf`），
否则光是扩展名检查就能挡住它，这条用例就测不到签名本身。

### 12.3 重新转换复用编辑保存那条流水线

`POST /api/documents/{id}/reconvert`：读原件 → 解析 → **直接调用 `update_document`**
（与"用户手改正文"同一个入口）。版本快照、向量替换、失败回滚、远端写回，它都已经处理过；
重新转换在后果上与手改正文是同一件事，另写一条流水线只会多出一份会漂移的补偿逻辑。

转换完把当前 revision 记回去，状态随之回到 `available` —— 否则用户点了"重新转换"，
提示还挂着，他会以为没生效。

三处拒绝都有独立原因码，且都不该退化成 500：
`DOCUMENT_ORIGINAL_NOT_LINKED`（拷贝型没有"原件被改"这回事，409）、
`DOCUMENT_ORIGINAL_MISSING`（原件没了，404）、`SOURCE_UNSUPPORTED`（签名不对，400）。

### 12.4 一个把用例从 500 秒拉到 2 秒的测试基建问题

写"重新转换"用例时先踩了个大坑：单条用例跑了 **500 秒**，还返回 503 `INDEX_FAILED`。
逐段打点后定位到 —— **任何走索引的请求都会为真的 BGE provider 付一次模型加载**，
本机实测一次 **519 秒**（`POST /api/repositories/{id}/documents` 同样中招，不只是我的新接口）。

既有用例之所以看起来很快，是因为同一个 pytest 进程里模型只加载一次，前面某条用例已经付过账；
**单独跑某一条要索引的用例时，这笔钱就得它自己出**。已新增 `indexed_client` fixture
（装上 `FakeEmbeddingProvider`）给需要索引的用例用，并把这笔账写在了 fixture 的注释里。
代价对比：同一组用例从 **523 秒 → 1.93 秒**。

顺带记一笔：探针里先写中文再写 ASCII 都没能变快，说明**与 OCR 无关** —— 期间另一个假设
（CJK 用 Helvetica 画不出来会被判成"需要 OCR"）是错的，真正的瓶颈就是模型加载。
真相是靠逐段打点拿到的，不是靠推测。

### 13.1 后端说得出，界面看得见

### 13.2 重新定位的对话框：`ANY_FORMAT`

重新定位最常见的情形恰恰是**原件已经不在磁盘上了**，所以后端给不出 `originalMediaType`，
界面无从知道它原本是什么格式。原先只有"按格式打开对话框"这一条路（`chooseSource(format)`），
逼界面猜一个格式名，猜错就被"不支持的扩展名"拒掉。

所以加了哨兵 `ANY_FORMAT`（声明在 `shared/contracts.ts`，主进程与渲染层共用一处声明），
主进程据此把所有受支持格式的扩展名拼成一个过滤器。`StagedFileService` 里的校验也抽成了
一个 `pickLinkedFile(formats, resolveFormat)`，`chooseAndLink` 与 `chooseAndLinkAny`
共用它 —— 两条路的安全检查不会各漂各的。

### 13.3 重新定位也必须签名，而且处理器要是 async

门与导入同一条：`documents:relinkOriginal` 处理器在转发前调 `withSignedPath`，只给
对话框登记过的路径签名。否则"重新定位"就是绕开导入那道门、把任一篇文档指到任意文件上的
第二条路。

写这条用例时踩到一个小坑：处理器最初写成非 async，而 `withSignedPath` 在未授权路径上是
**同步抛错**，调用方（IPC 包装层）按 promise 处理失败 —— 同步抛出会绕过它。改成 `async`
（与 `imports:inspect` 一致）之后，同步抛错自然变成 rejection。已在这行加了注释说明
async 在这里不是风格而是必需。

## 十四、已落地：阶段 3 的后端（目录批次就地读）

### 14.1 清单从"一堆副本"变成"一个指针"

关键发现：**清单里原本就记着 `relativePath` 与 `sha256`**，核对摘要的机器
（`read_file_snapshot`）也早就为"防止读取期间被换掉"而存在。所以不必新写一套，
只需让"这条记录的字节在哪"换一个答案：

```
staging/collections/<id>/manifest.json          ← 仍然只有这一份清单，没有 items
  { rootId, rootPath, rootToken, files: [ {relativePath, stagedId, mediaType, sizeBytes, sha256} ] }
                     ↑ 新增：用户授权的那个目录（带主进程签名）
```

字节要么来自 `collections/<id>/items/<stagedId>`（拷贝型，今天的行为），
要么来自 `<rootPath>/<relativePath>`（链接型）。**这个问题的答案只在一个地方**
（`staging_manifest.entry_path`）—— 校验、发现、导入三处各自拼一次路径，
迟早会有一处忘记做包含性检查。

`stagedId` 两种形态都保留（链接型由主进程给一个随机 UUID 当句柄）：这样
`CachedSourceRef`、批次的 `cached_source_json`、`_validate_descriptor` 全都不用动。
它只是个句柄，不再必须对应一个真实文件名。

### 14.2 一致性保证没有降级

用户确认的是清单里那份快照（每一项的 sha256），读取时**逐项重新核对**：文件在"确认"
之后被改过，那一条就以 `BATCH_SOURCE_CHANGED` 失败 —— 与拷贝型完全一样。
差异只有一个：拷贝型读的是我们自己的副本，链接型读的是用户目录里的文件。

引用里只有**相对路径**（`display_path = relativePath`、`source_identity = folder:<rootId>:<relPath>`），
用户目录的绝对路径不进 chunk、不进引用。

### 14.3 门：`DIRECTORY_DOMAIN` 签名

清单里的 `rootPath` 必须带主进程签名（域与单文件分开，所以"授权了一个文件"不能被当成
"授权了一个目录"）。没有密钥、签名不对、目录不存在 —— 一律 `BATCH_SOURCE_CHANGED`，
**默认拒绝而不是默认信任**。

### 14.4 两次变异实验教我的事

第一轮变异：去掉包含性检查 → **测试全绿**；去掉摘要核对 → **测试全绿**。
两次都"活下来了"，原因不是测试写错，而是**同一件事有两道检查**：

- 包含性检查在 `validate_manifest` 与 `DirectoryDiscovery._candidate` 各有一道；
- 摘要核对在 `validate_manifest` 与 `_candidate` 的 `read_file_snapshot(expected_hash=…)` 各有一道。

防御纵深是好事，但它让"哪一道坏了"变得不可见。于是补了两条**直接打在校验层**的用例
（绕过 discover），并把变异改成"两处一起拿掉"才验证出来。

第二轮又发现第二个问题：`test_a_file_changed_after_confirmation_is_caught` 原本把文件
写成更长的内容，于是**大小检查**先拦下了它 —— 那意味着"只删掉摘要核对"这个变异测不出来，
绿得虚假。改成**写入等长内容**（`# Beta\n` → `# Beto\n`，都是 7 字节）之后，
只有摘要核对能发现它。修完再跑同一个变异：两条用例如期变红。

教训写在这里：**"测试变绿"不等于"测试在测你以为的那件事"**。防御纵深与多条件的
守卫都会掩盖变异，只有真去跑变异才能发现。

## 十五、已落地：阶段 3 的主进程扫描器（目录批次真正就地读）

### 15.1 清单由主进程写，授权不经过渲染层

`scanSelectedDirectory(selectedPath, options)`：走与复制路径**同一个准备阶段**
（canonical 化、限额、候选清单、rootId —— 抽成了 `prepareDirectoryScan`，两条路共用），
区别只在每个文件：那边把字节拷进 `items/`，这边只流式算一个 sha256，然后把
`rootPath` + `rootToken`（`DIRECTORY_DOMAIN` 签名）写进清单。

一个和单文件不同的性质：**这条授权不经过渲染层**。清单是主进程直接写进暂存目录的，
渲染层只拿到 `{collectionId, displayName, itemCount, totalBytes}` —— `displayName` 是目录的
**basename**，不含路径。所以"渲染层不能指名任意目录"这件事在这里连签名都不需要：
它没有写暂存目录的能力。

`stageDirectory`（目录选择对话框）已改走扫描器；`stagedId` 仍然每项一个 UUID，
它只是把清单条目与批次项对上的句柄，于是批次那一整套数据结构一行没动。

### 15.2 复用与删除

- 复制型的 `atomicCopyCandidate` **保留**（这一轮不删）：它和 `hashCandidate` 共享
  `matchesCandidate`、`assertInsideRoot`、`collectCandidates` —— 目录扫描的安全性质
  （不跟符号链接、打开前后核对设备号/inode/mtime/ctime、逃逸检查）本来就都在这些函数里。
- `hashCandidate` 就是 `atomicCopyCandidate` 去掉"写副本"那半边，检查一条不少。
- 6 条既有的目录安全用例（限额、符号链接、rootId 注册表、超大文件、读完之后被替换）
  改指向扫描器 —— 它们测的性质对两种形态同样成立，于是**同一批用例现在守着新代码**。

### 15.3 一次真实的删除事故（记下来，因为它正是 AGENTS.md 警告的那件事）

我在删掉被取代的复制型目录写入器时，用"从某个文档注释到下一个类型声明"这种**开放上界**
做切片。结果那次切片多吞了三个方法：`chooseAndStage`、`stageSelected`，以及
`stageDirectory` —— **目录导入的服务入口本身**。tsc 立刻报了 `scanSelectedDirectory` 未定义，
顺着查才发现丢的远不止预想的那一个函数。

恢复方式：`git checkout` 把该文件退回 HEAD，然后**只重放加法改动**（新增类型/方法/扫描器 +
把 `stageDirectory` 指向扫描器），这一轮不做任何删除。事后回看，两件事值得记住：

1. 开放上界的切片在"我以为是 A 到 B"的地方，实际删的是 A 到 C。要用**有界**替换
   （精确的起止字符串），而不是"从某处到下一个什么"。
2. 想删的东西和被误删的东西**混在一次编辑里**时，出错的代价是"功能没了但类型检查可能还过"。

### 15.4 跨语言契约：清单的键名

清单是主进程写 JSON、后端用 pydantic 的 alias 读。两边各自的测试都发现不了拼写漂移：
Python 那份手写自己的 JSON，主进程那份只断言自己写出来的形状。所以新增一条用例，
**去读后端的模型声明**逐字比对（与 `contracts.test.ts` 里 `MODEL_PRESET_IDS`/`SOURCE_KINDS`
同一套做法）。变异验证：把 `rootPath` 写成 `root_path`，两条用例变红。

写这条用例时踩了两个小坑，都留在注释里：字段名可能带数字（`sha256` —— 用
`[a-z_]+` 会整条漏掉），以及 `files` 是没有 alias 的字段（JSON 键就用字段名）。

## 十七、后台扫描 + 进度 + 取消（阶段 3 收尾的体验补丁）

### 17.1 从前的问题：一次调用读完整个目录

扫描要把用户目录里每个文件**完整读一遍算摘要**（不复制），几百个文件就是几分钟。而它原本
发生在"选完文件夹"那一次 IPC 的里面 —— `sources:stageDirectory` 一问一答，扫完才返回。
界面只能等：没有进度、没有取消，用户不知道是在干活还是卡住了。

### 17.2 现在：订阅式，一个 id 走完全程

```
渲染层：sources.scanDirectory(requestId, onEvent)   ← 立刻拿到订阅句柄
  主进程：立刻返回，后台逐个文件算摘要
     progress {scanned, total}   数量来自遍历目录项，所以总数在第一个文件读完前就是准的
     done     {collection}       拿到清单 → 照旧建批次、发现
     done     {collection: null} 用户取消
     error    {code, ...}        走既有的 serializeIpcError（文案住在前端）
  取消：既有的 streamCancel → stagedFiles.cancelScan(id) → 删掉 .partial 清单目录
```

复用的是这个仓库已有的推送机制（`PUSH_CHANNELS` + `streamEventChannel` + preload 的
`subscription` 助手），没有新造一套。事件类型沿用既有的 `progress|done|error` 枚举。

界面侧：扫描期间显示 `TaskProgress`（"已扫描 12/300" + 进度条 + 取消按钮），
并且**不再显示"选择目录"** —— 否则会同时跑两个扫描。关闭对话框会**取消**扫描
（不只是停止监听）：后台任务在读用户的磁盘，没人要的结果不该继续跑完、更不该留下一份
没人引用的清单。

### 17.3 写用例时抓到的一个真 bug：两个 id

最初 handler 把**渲染层给的 requestId** 用来路由事件流，而服务内部又 `randomUUID()` 生成了
一个 scanId 用于取消 —— 于是 `streamCancel(id)` 永远查不到正在跑的扫描：**调用发生了、
什么也没停**。而任何"断言 cancelScan 被调用过"的用例都发现不了这件事。

改成**一个 id 走完全程**：id 由调用方给（它同时是事件流的路由键与取消键），服务不再自己
生成。这条性质现在有专门断言：`scanDirectory` 收到的第二个参数必须等于调用方给的 id。

### 17.4 测试与变异验证

| 用例 | 守着什么 |
|---|---|
| `reports the total before the first file is read, then counts up` | 进度序列是 0/3、1/3、2/3、3/3 —— 总数先于任何文件读取 |
| `cancels mid-scan and leaves no half-written collection behind` | 取消后是 `cancelled` 而不是 `error`；**并且真的早停**；`collections/` 里连 `.partial` 都没有 |
| `cannot be cancelled once it has finished` | 跑完之后取消不生效（幂等） |
| `streams a directory scan back under the caller's own id` | 进度/结果走在同一个 id 的流上；`scanDirectory` 拿到的就是那个 id；绝对路径不出主进程 |
| `routes a scan cancel through the same id it started with` | 取消用的 id 与开扫用的 id 相同 |
| `rejects a malformed scan id before touching the backend` | 非法 id 在校验层就被挡下 |
| `shows scan progress and lets the user stop a long scan`（渲染层） | 进度可见、扫描期间不给"再选一次"、取消按钮接上了取消 |

变异验证：拿掉"先报总数" → 1 条红；拿掉循环里的取消检查 → 1 条红（**这条一开始没红**，
因为只断言了"最终是 cancelled"，而写清单前还有第二道检查兜着 —— 补上"真的早停"的断言
之后才杀掉）；把 handler 的 id 换成内部另生成的一个 → 1 条红（**同样一开始没红**，
补上"scanDirectory 收到的就是调用方的 id"之后才杀掉）。

两次都是同一个教训的变体：**断言最终状态不够，要断言那条性质本身**。

  557 通过 / 17 失败**（17 条仍是 `panel-resize` 那组既有失败）

## 十八、中断之后的两处收口

### 18.1 被中断的扫描留下的 `<id>.partial` 立刻清掉，不等宽限期

扫描只在**进程内**存在，`<collectionId>.partial` 这个后缀就是"尚未发布"的标记；而对账清扫
跑在启动时 —— 那时不可能有扫描在跑。所以启动时看到的每一个 `.partial` 按定义都是孤儿，
24 小时宽限期只是让垃圾多躺一天。

规则因此单独分出来（`_is_partial_scan` + 独立的 `partial_scans` 计数）：

| 目录 | 规则 | 为什么 |
|---|---|---|
| `collections/<id>.partial` | 立刻删（无条件） | 半成品；进程内才有意义，启动时必然无主 |
| `collections/<id>` | 看引用与时间 | 可能是别的进程正在用的集合，宁可漏删 |

注意 `.partial` 的判定只认**这一层**的后缀：清单与来源注册表自己也会用
`xxx.<uuid>.partial` 这种临时文件，但它们在目录**内部**，随目录一起被删。

两条新用例都拿**真实宽限期（24 小时）+ 刚写出来的半成品**来测，所以谁把 `.partial` 挪回
宽限期分支都会立刻变红；其中一条还断言"就算有批次（硬造的描述符）引用了这个名字也照删"。
变异验证：把那条规则关掉 → 2 条红。

### 18.2 一句过时的文案

主进程把 `BATCH_SOURCE_CHANGED` 映射成「目录内容在**暂存**期间发生变化」，而现在已经不暂存
了 —— 改成「扫描期间」。改的是用户**看得到**的那一处（`stagedMessages`），它有用例钉着。

后端内部还有一批 `暂存文件…` 之类的措辞（`sources.py` / `staging_manifest.py`），它们只在
没有映射的原因码上才会露到界面上，属于日志与内部语义，**这次没动** —— 要动是一次独立的、
有界的措辞清理（会牵连若干断言了文案的用例）。

### 18.3 验证

后端全量 **1779 passed**（含新增 2 条），`ruff check app tests` 通过；前端 `tsc`、
`eslint --max-warnings=0`、`prettier` 通过，`vitest run` **574 条 / 557 通过 / 17 失败**
（17 条仍是 `panel-resize` 既有失败）。两处改动都做了变异验证。

至此"突然中断"的三种情形各有归宿：**取消/失败**当场清理（有用例）；**进程被杀/断电**

## 十九、以原格式修改原件（"用系统程序打开"）

### 19.1 为什么不做"应用内写回 docx/pdf"

用户要的是"以**原格式**改原件"。应用内写回看起来更顺手，但它会毁掉这个诉求本身：
流水线只有解析器（pdf/docx/html/markdown → Markdown），没有写入器；而"Markdown → docx"
必然有损 —— 样式、批注、修订、图表、编号、页眉页脚。用户改一个词、回来发现版式没了，
比不能在应用里改更糟。PDF 更是没有可编辑的文档模型。

所以正确的形态是：**让 Word 去改 Word**，应用只负责两件事 —— 打开它，以及察觉它变了。
后者（`changed` 状态 + 重新转换）在前面的阶段已经做完了。

### 19.2 打开这一跳怎么保住"渲染层不能指名任意文件"

新增 `GET /api/documents/{id}/original-location`：返回原件的路径 + 一份
`FILE_DOMAIN` 签名，以及 `state`。主进程拿到之后**自己验签**，再交给 `shell.openPath`。

关键是**主进程必须自己验**，不能"请求后端 → 拿 path → 打开"：那样权限实际落在"谁能影响
这次请求"上，而渲染层能影响的正是 `documentId`，签名就白签了。验签用的是
`pathTokenMatches`（`timingSafeEqual`，与后端一致），渲染层从头到尾看不到 path 与 token。

原件读不到时这个端点**不报 404**，而是 `path=null` + `state`：`missing`（绑定过但丢了，
界面出口是「重新定位原件」）与 `none`（本来就没有原件）必须继续可区分 —— 报 404 会把
这两种情形在界面上抹成一样，而那正是前面特意分开的东西。

### 19.3 界面

- **头部新增「用系统程序打开原件」**（仅在 `available`/`changed` 时出现）：`missing` 时
  上面那条横幅已经给出唯一正确的出口（重新定位），再摆一个灰按钮只会诱人去点它。
- **重新转换前先确认**：`ReconvertOriginalDialog` 说明"整篇替换正文；应用内改过的会进
  版本历史"。入口一律先过它 —— "原件已更新"这个提示本身就在鼓励用户去原件里改，
  改完回来点重新转换正是最容易顺手抹掉应用内改动的那条路径。
  为什么不是"只在改过的时候才问"：后端没有"被手工编辑过"的标记，而拿"版本历史里有没有
  快照"去猜是错的（重新转换本身也会存快照）。宁可在每次问一句，也不要一个会漏报的猜测。

### 19.4 测试与变异验证

| 用例 | 守着什么 |
|---|---|
| `original_location_gives_main_a_signed_path`（后端） | 端点发的签名能被**后端自己的**验证函数验过；换路径就验不过 |
| `original_location_separates_missing_from_never_linked`（后端） | `missing` 与 `none` 在最后一跳仍可区分 |
| `verifies the backend's signature before letting the system open the file`（主进程） | 验签通过才 `openPath` |
| `refuses a path whose signature does not match`（主进程） | 换了路径带着旧签名 → 拒绝，**且没有被打开**（只断言"抛错了"会漏掉"先打开再报错"） |
| `refuses a token signed for a different path in the same domain` | 签名绑在路径上，不是一张通行证 |
| `separates a missing original from a document that never had one`（主进程） | 两种情形两个原因码 |
| `surfaces the system's failure as a stable reason code` | `openPath` 返回非空串（没有关联程序）→ 稳定原因码，不吞掉 |
| `asks before reconvert overwrites edits, and only then reconverts`（界面） | 确认前 `reconvert` **一次都没被调用** |
| `does nothing when the reconvert confirmation is cancelled` | 取消就什么都不做 |
| `opens the original with the system program, sending only the document id` | 渲染层只发 documentId |
| `does not offer to open an original that is gone` | `missing` 时没有"打开"入口 |

变异验证：**不验签就打开** → 2 条红；**重新转换不再确认** → 2 条红。

### 19.5 验证与边界

- 后端全量 **1781 passed**（含新增 2 条），`ruff` 通过
- 前端 `tsc` / `eslint --max-warnings=0` / `prettier` 通过；`vitest run` **582 条 /
  565 通过 / 17 失败**（17 条仍是 `panel-resize` 既有失败）
- **没跑**：真机手测。"用系统程序打开"这一步依赖 Electrons 的 `shell.openPath` 与系统的
  文件关联（macOS 上还可能弹 TCC 授权），只有真机能验；主进程那一跳是用注入的假
  `openPath` 测的。另外"macOS 上 .docx 没有关联程序"这类环境差异，界面上给的是
  `DOCUMENT_OPEN_FAILED` 的通用文案。
