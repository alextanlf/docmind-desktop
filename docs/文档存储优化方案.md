# 文档存储优化：导入副本 × 转换副本

> 2026-10-12 · 基于本机真实数据目录实测（`~/Library/Application Support/docmind-desktop`）
> 与源码核对，非推断。
>
> **状态**：L1（原件分层保留）与「文件名被 UUID 顶掉」已落地，见第七节；
> L0（暂存清理）、L2、L3、L4 仍是设计。
>
> **后续**：本文写的是 `documents/<id>/raw.bin`。这个不带扩展名的名字后来被发现会毁掉
> 「用系统程序打开原件」（系统按后缀选应用 → 丢给归档实用工具），已改成 `raw.<后缀>`
> —— 见 `本地原件直读方案.md` 第十九.6 节。下文保留当时的实测数据与结论，
> 名字按当时的形态写。

## 一、先说结论

一次「导入文件 → 格式转换成 Markdown」，磁盘上实际产生 **5 份内容**，其中 **3 份写进去之后再没有任何读取点**：

| # | 位置 | 谁在读 | 本机实测 |
|---|---|---|---|
| 1 | `documents/<id>/raw.bin` | **只有 PDF 原件视图**（Range 分页） | 1,137,803 B |
| 2 | `documents/<id>/document.md` | 阅读、编辑、检索、引用 | 50,052 B |
| 3 | `imports/staging/<uuid>.<ext>` | **无人读**（导入结束后就是垃圾） | 1,137,803 B |
| 4 | `imports/staging/collections/<id>/` | **无人读**（批次结束后） | 2,140 KB |
| 5 | SQLite `document_chunks.text` | 检索（同一份文本的第二遍） | 52,965 B / 31 块 |

`documents/` 一共 1,168 KB，**其中 95.8% 是 `raw.bin`**；而 `imports/` 里躺着 3,260 KB 从未清理的暂存副本 —— **比正式存储还大 2.8 倍**。

所以「优化保存方式」的答案不是换一种压缩或换一个存储后端，而是**把"写进去没人读"的副本去掉，并把原件按"有没有阅读器"分层保留**。

## 二、原件 `raw.bin` 到底谁在读（源码核对）

```
GET /api/documents/{id}/raw          ← 唯一读取点（api/documents.py:1091）
  └─ FileResponse（Starlette 处理 Range）
       └─ preload readOriginalChunk   (preload/index.ts:309)
            └─ PdfOriginalView        (features/repositories/PdfOriginalView.tsx)
```

而原件视图的挂载条件是 **只认 PDF**：

```ts
// features/repositories/DocumentEditor.tsx:39
document.originalMediaType === "application/pdf" && (document.originalByteSize ?? 0) > 0
```

`_original_info()` 只嗅探 PDF magic，其余一律返回 `application/octet-stream`（`api/documents.py:120-137`）。于是：

- **docx / .pages / markdown 的 `raw.bin` 是纯写入、零读取。**
- 仓库里**没有「重新解析」功能**（`rg "重新解析|reparse"` 只命中依赖库注释），所以"留着原件以便换解析器重跑"目前是不存在的需求，不该为它付 95% 的存储。
- URL 源更极端：`_run_upload` 推远端时读的是 `document.markdown_path`（`imports/service.py:501`），原件在转换完成后对全流程再无用处。
- markdown 源最直白：`raw.bin` 2,282 B 与 `document.md` 2,281 B **只差 1 字节**，同一份文本存了两遍。

## 三、方案

### L1（首推）：原件按「有没有阅读器」分层保留

不是"要不要存原件"，而是**把 `raw_path` 的语义从"导入时的输入字节"改成"原件视图可用的字节"**。

| 格式 | 原件用途 | 处理 |
|---|---|---|
| PDF | 原件视图（Range 分页，pdfjs 依赖真实字节） | **保留** |
| 图片（若将来支持） | 原件视图 | 保留 |
| docx / .pages / epub | 无任何读取点 | **不落盘** |
| markdown / txt | 内容即转换结果本身 | **不落盘** |

改动面（估算）：

- `imports/service.py:844` 的 `raw_path.write_bytes(...)` 加一个 `format.keeps_original` 开关（`DocumentFormat` 已有 `binary_payload`/`magic` 这类格式自述字段，加在这里符合现有结构）。
- 不落盘时 `DocumentRecord.raw_path = None`。`_original_info()` 已经对缺失原件返回 `(None, None)`，前端自动不显示原件视图 —— **零 UI 改动**。
- 设置页「本地数据」面板（`LocalDataPanel.tsx`，已有"清理失败截图"那一套）加一个「保留原件」开关，默认关；`.pages` 这类转换昂贵、依赖外部 App 的格式，用户可勾选保留。

**预期收益**：本机 1,137,803 B → 1,115,604 B（只留 PDF），省 22 KB；但这是"3 篇样本"的数字。真实收益随 docx/pages 占比放大 —— 按当前样本，非 PDF 文档的原件占其自身存储的 **71%**（docx）。要拿真实分布，先跑第六节的测量脚本。

**要红在哪**：断言"docx 导入后 `documents/<id>/` 下不存在 `raw.bin`"、"导入 docx 后原件视图属性为空而不是 500"、"PDF 导入后 Range 分页仍可用"。

### L0：清理暂存副本（已落地，见第八节）

现象：`imports/staging/<uuid>.<ext>` 和 `collections/` 在导入结束后**从不删除**。

核对结果：整个仓库（排除 `node_modules` / `dist`）里，对 staging 只有写、没有删：

- 写单文件：`electron/main/staged-files.ts:175-230`（UUID 命名，防路径注入）
- 写集合：`staged-files.ts:302-330`
- 后端读：`document/sources.py:109-156`、`196-271`
- 删除点：**没有**（`main.py` 也没有启动清理）

本机证据：staging 里 3 个文件合计 1,137,803 B，与 `documents/*/raw.bin` 合计**逐字节相同**（同一份文件的第二次拷贝），加上 `collections/` 2,140 KB，共 3,260 KB。

设计要点（含一处真实取舍）：

1. **单文件删除时机**：job 进入**成功终态**后删。不能失败即删 —— `ImportService.retry` 会重新 `load(ref)`（`imports/service.py:427`），staging 没了重试就断。失败/取消要留到用户明确「放弃导入」或关闭对话框。
2. **集合删除时机**：manifest 校验要求 items 在整个批次期间存在（`sources.py:202-271`），所以删除时机 = 批次终态。批次中途删会让后续 item 全部报 `BATCH_SOURCE_CHANGED`。
3. **兜底清扫**：启动时扫 `staging/`，删除超过 N 小时（建议 24h）的孤儿 —— 覆盖崩溃后残留。
4. ~~**删除点放哪**：建议放在 electron 主进程，渲染层在 job 终态时调 `discardStaged(stagedId)`。~~ **实际做法反过来了**：不挂 IPC，改成后端按数据库对账 —— 理由见第八节第 1 条，那是这份设计里唯一被推翻的决定。
5. 同一目录下还有**第三类残留**：`staging/remote/<batchId>/`（`api/web_search.py:47-52` 写入，未找到删除点）。清理策略要一并覆盖，否则等于只扫了半间屋子。

**要红在哪**：断言"导入成功后 staging 目录不再有该 stagedId"、"导入失败后重试仍成功"、"崩溃残留的孤儿文件在启动清扫中被删"。

### L2：内容寻址去重（治重复导入，不治格式转换）

现有查重是 `find_by_hash(repository_id, content_hash)`（`storage/repositories.py:328`）—— **按仓库隔离**。同一份 PDF 导进两个知识库，`raw.bin` 与 `document.md` 各存一份。

- 改成 `blobs/<sha256[:2]>/<sha256>` + `documents` 存引用，跨仓库自然共享；删除时按引用计数回收。
- 收益完全取决于用户是否重复导入，**优先级低于 L0/L1**。但它同时是 L4 的前置（版本快照也想复用同一套 blob），所以值得作为后续统一抽象，而不是为省空间马上做。

### L3：chunks 与 markdown 的重复（建议先不动）

实测：31 块 / 52,965 B 的 chunk 正文 ≈ 三份 `document.md` 之和（50,052 B）。同一份文本在 SQLite 里又存了一遍（外加 FTS 索引本身）。

- 可选做法：FTS5 external-content 表 + chunk 只存 markdown 的行偏移。
- 但它改的是**检索层**，需要重跑召回基线（`backend/scripts/ab_*.py` 那一套，连同 JSON 结果）。收益与 `document.md` 同量级（几万字节），**风险收益不成比例，建议等 L0/L1 落地后重新量一次分布再定**。

### L4：版本快照（当前 0 行，属潜在问题）

`VersionStore.snapshot` 每次保存把**全文**写进 SQLite，上限 20 份（`storage/repositories.py:2982-3015`）。本机 `document_versions` 是 0 行，但形态一旦被用到就会很难受：一篇 500 KB 的 Markdown 改 20 次 = 约 10 MB 的 SQLite，而且 `DELETE` 不归还文件空间（需要 `VACUUM`）。

- 建议：复用 L2 的 blob（版本表只存 `content_sha256` + 标题），或直接落成 `documents/<id>/versions/<n>.md`（普通文件，删除即归还空间）。

## 四、顺手发现的两个真实缺陷（与存储同源）

1. **文件名被 UUID 顶掉成标题。** `StagedFileStore.load` 用 `title=path.name`（`document/sources.py:148`），而暂存文件名是防注入用的 UUID。本机 3 篇里 **2 篇的标题就是 `0d17078a-3664-4b9d-b2ee-…`**（PDF 的 `docProps` 无标题、docx 的 `core.xml` 无标题时，都回落到 `document.title`）。
   electron 侧其实已经拿到了原始文件名（`staged-files.ts:238` 返回 `name: basename(source)`），只是渲染层只往上送了 `stagedSourceId`（`SourceStep.tsx:39`）。**把 name 一起传上来即可** —— 一行数据流的事，但影响的是用户看到的第一眼。
   注意源码注释里"不要把暂存绝对路径暴露到预览、chunk、引用"的约束仍然成立：这里要传的是**用户自己选的那个文件名**，不是路径。（已落地，见第七节。）

2. **markdown 文档存了两份**（`raw.bin` 与 `document.md` 差 1 字节）—— L1 直接消掉。（已落地。）

## 五、落地顺序

| 顺序 | 项 | 风险 | 收益 | 依赖 |
|---|---|---|---|---|
| 1 | L1 原件分层保留 | 低（读点已全部核对） | 高（非 PDF 省 70%+） | 无 |
| 2 | 标题修复（四-1） | 低 | 用户可见 | 无 |
| 3 | L0 暂存清理 | 中（终态/重试语义） | 最高（本机 2.8×） | 新 IPC |
| 4 | L2 内容寻址 | 中 | 视重复导入 | 无 |
| 5 | L4 版本快照瘦身 | 中 | 潜在 | L2 |
| 6 | L3 chunk 正文 | 高（检索层） | 低 | 先量分布 |

## 六、先量再改（照 AGENTS.md 的规矩）

在真实数据目录上跑这三条，拿到自己机器上的分布再决定 L1/L2 的取舍：

```bash
D="$HOME/Library/Application Support/docmind-desktop"
# 1) 每篇文档：转换结果 vs 原件
for d in "$D/documents"/*/; do
  stat -f "  %z  %N" "$d"document.md "$d"raw.bin 2>/dev/null | sed "s|$D/documents/||"
done
# 2) 从未清理的暂存副本
du -sk "$D/imports"; find "$D/imports/staging" -maxdepth 1 -type f -exec stat -f "%z %N" {} \;
# 3) chunk 正文 / 版本快照在 SQLite 里的体量
sqlite3 -readonly "$D/database/docmind.sqlite3" \
  "select (select sum(length(text)) from document_chunks) chunk_bytes,
          (select count(*) from document_versions) versions,
          (select coalesce(sum(length(content)),0) from document_versions) version_bytes;"
```

判据建议（先写死判据再改，避免"改完再看效果"）：

- 若 `sum(raw.bin) / sum(all) > 50%` → L1 立刻做。
- 若 `imports/` 体积 > `documents/` → L0 的优先级提到 L1 之前。
- 若 `version_bytes > 5 MB` → L4 提前。

## 七、已落地：L1 + 标题修复（本次改动）

### 7.1 原件只在「有人能显示它」时落盘

判断依据挂在**格式声明**上，不是散落在导入流程里的 `if media_type == "application/pdf"`：

```python
# document/formats.py
original_viewable: bool = False   # 应用能不能把这份字节渲染回给用户

# document/builtin_formats.py —— PDF 是唯一一个 True
```

`_persist_parsed_document` 据此决定写不写 `documents/<id>/raw.bin`；不写时 `raw_path` 存 `None`，
并顺手删掉同一目录下可能的历史 `raw.bin`（否则「记录说没有、磁盘上躺着一份」，磁盘占用与数据库对不上）。

没有加「保留原件」开关，是刻意的：现在既没有重新解析功能，也没有 docx/pages 的原件阅读器，
开关打开也只是把空间换成一个用不上的文件。等真要做重解析时，开关和 blob 回收一起加更合适。

### 7.2 文件名贯通：`SourceRef.name`

- 渲染层：`SourceStep.tsx` 把 `staged.name` 一起送进 `SourceRef`（此前只送了 UUID）。
- 契约：`contracts.ts` 的 `SourceRefSchema` 增 `name`，老客户端不发也能跑。
- 后端：`StagedFileStore.load(staged_id, display_name)` 用 `display_title()` 收敛后当标题。
- **重试路径**：`name` 与 `value`/`fingerprint` 并列写进 job 的 `source_value` JSON，重试与
  `_run_parsing` 重建 `SourceRef` 时一起取回。不存这一份，重试出来的标题会退回 UUID。
  metadata 版本号不升（仍是 2）：新增键对老记录只意味着「没有这个名字」，语义不变。

`display_title()` 只取 basename、丢控制字符、压平空白、截到 **240** 字符 —— 取 240 而不是标题列的
1024，是因为客户端 `SourcePreviewSchema.title` 是 `text(240)`，超了会在 IPC 边界被拒，
用户看到的是「导入失败」而不是一个长标题。

**一个差点带上线的跨语言坑**：后端 `SourceRef.name` 可空，FastAPI 又没带 `exclude_none`，
所以 URL 导入与老记录的响应里是显式的 `"name": null`。zod 只写 `.optional()` 时放过「键缺席」、
卡住「显式 null」，导入进度接口会在 IPC 边界整个被拒 —— 而 vitest 用的假 API 根本不带这个键，
**全绿也抓不到**（这条是靠核对 pydantic 的序列化结果发现的，不是靠测试发现的）。
正确写法是 `.nullable().optional()`，并由 `contracts.test.ts` 新增的三条断言守住。

## 八、已落地：L0 暂存清扫（本次改动）

### 8.1 设计上被推翻的一点：不挂 IPC，改成按数据库对账

第七节之前的设计是"传给渲染层一个 `discardStaged(stagedId)`，job 终态时调一下"。
真去接的时候发现这条路要绕开三件事：

1. **写入者有三个，删除者却只能有一个。** 单文件与目录集合由 electron 主进程写
   （`staged-files.ts`），网页/远程缓存由后端自己写（`web_search.py:47`、`remote/discovery.py:68`）。
   挂在渲染层意味着"后端写的东西要等前端来通知才删"。
2. **"还会不会再读"这件事只存在于数据库里。** 磁盘上没有能回答它的信息，而数据库里有
   任务状态与批次状态。既然判定依据在数据库，删除点放在数据库旁边（后端）比放在路径
   属主（主进程）更顺。
3. **批次终态有 4 个写入点**（`fail_discovery`、`set_state`、`finish_cancel`、
   `recover_on_startup`），挂在某一个流程出口上必然漏掉其它三个。

所以改成 `app/imports/staging_cleanup.py` 里的**对账清扫**：不关心是谁写的、什么时候写的，
只回答"谁还会再读它"。它对崩溃天然免疫 —— 崩在导入中途留下的副本，下次启动照样收掉。

### 8.2 两条通道，各管一半

| 通道 | 时机 | 覆盖 |
|---|---|---|
| 即时删除 `ImportService._discard_staged_source` | job 变 COMPLETED / CANCELLED 的那一刻 | 单文件副本（长跑的应用不会攒垃圾） |
| 对账清扫 `StagingReconciler.reconcile` | 启动时，排在两个 `recover_*` 之后 | 三类全收：单文件、`collections/`、`remote/` |

启动那条必须排在 `ImportJobStore.recover_interrupted()` 与 `BatchService.recover_on_startup()`
之后：它们先把"中断"改判成 FAILED/CANCELLED，磁盘上的副本才对得上"谁还会再读"。

### 8.3 可删的终态是**窄**的

| 对象 | 可删 | 必须留 | 为什么 |
|---|---|---|---|
| 导入任务 | COMPLETED、CANCELLED | PENDING/PARSING/UPLOADING/INDEXING、**FAILED** | FAILED 可能重试，且重试可能从 PARSING 恢复（`reset_for_retry` 用的是 `current_stage`） |
| 批次 | COMPLETED、FAILED、CANCELLED | RUNNING/PAUSED/DISCOVERING/AWAITING_CONFIRMATION、**COMPLETED_WITH_ERRORS** | `retry_items` 明确把 COMPLETED_WITH_ERRORS 移回 RUNNING |

"没人引用"的副本（崩溃残留、用户选好文件还没确认）只能靠**时间**区分，所以加了
`staging_orphan_grace_seconds`（默认 24 小时）。它同时保护着主进程的 `.partial`
半成品 —— 那是"正在拷贝"的副本，天生没有任务引用。

### 8.4 删除集是白名单

不认的东西一律不碰：名字不是 UUID 的文件、`collections/` 与 `remote/` 下的非目录、
以及符号链接（用 `lstat` 判，`is_dir()` 会跟着链接走到目录树外面去）。
描述符坏掉的批次**跳过而不是猜**，跳过的数量进报告 —— 宁可漏删，不可错删。

### 8.5 测试与变异验证

`tests/imports/test_staging_cleanup.py` 25 条 + `test_service.py` 2 条。逐个做过变异验证，
即"把行为改回旧样子，对应用例必须红"：

| 变异 | 变红的用例 |
|---|---|
| 拿掉 COMPLETED 后的即时删除 | `test_completed_import_deletes_its_staged_copy` |
| `_fail` 里也调用即时删除 | `test_failed_import_keeps_its_staged_copy_for_the_retry` |
| 把 FAILED 加进可删集合 | `test_failed_job_staged_file_survives_the_grace_window` |
| 把 COMPLETED_WITH_ERRORS 加进可删集合 | `test_unfinished_batch_collection_is_kept[completed_with_errors]` |

恢复后用 `shasum` 逐字节比对确认无残留改动。

### 8.6 边界与未尽事项

- 对账清扫**只在启动时**跑一次。一个连续开着的应用里，批次集合与远程缓存要等到下次
  启动才回收（单文件不会，它有即时通道）。要不要再加一个周期性触发，等有了真实体量再说。
- 清理动作会写日志（`logger.info` 报删了多少、`logger.warning` 报跳过了几个坏描述符），
  有一条 caplog 用例钉着警告那条。`main.py` 仍然丢弃返回的报告对象 —— 将来加周期触发时
  它会派上用场。
- **没跑**：Playwright e2e。所以"真实导入一次 → 暂存目录真的空了"这条端到端路径依旧只有
  服务层与对账层的用例各守一半。

### 8.7 与并行实现的取舍：为什么只留一份

落地过程中，工作区里并行出现了**第二份 L0**：electron 主进程的 `pruneStagingOrphans`
（24 小时 TTL，只删 `staging/` 根下的单文件）。两份都留下会造成一个具体的坏结果，
不是"重复但无害"：

- 它挂在 `app.whenReady()` 的最前面，**早于后端启动**；后端随后才做
  `recover_interrupted()` 与对账清扫。也就是说它先删，后端的判定根本没机会生效。
- 它的规则不看数据库，所以会把一个**引用它的任务仍是 FAILED、还可能从 PARSING 档重试**
  的副本删掉（那正是 8.5 里被变异验证钉住的性质）。用户点「重试」只会得到
  `SOURCE_UNSUPPORTED`。
- 覆盖面也小：它按自己的注释明确不碰 `collections/` —— 而本机实测里集合残留
  （2,140 KB）比单文件（1,137,803 B）还大。

**结论：留后端的对账清扫，删掉 electron 那份。** 唯一的代价是清扫依赖数据库；
但两份清扫里更简单的那份之所以简单，是因为它把"谁还会再读"这个真正的问题换成了
"有多久没人碰"。后端本来就已经持有数据库，这个依赖不构成新的耦合。

（被删掉的是 `electron/main/staged-files.ts` 里的 `pruneStagingOrphans`、
`DEFAULT_STAGING_TTL_MS`，`electron/main/index.ts` 里的启动调用，以及
`electron/tests/main/staging-prune.test.ts`。那两个源文件还原到 HEAD —— 它们当时的
改动只有这份清扫，没有别的编辑。）
