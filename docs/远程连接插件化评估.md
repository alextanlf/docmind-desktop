# 远程连接插件化：现状、bug 修复与 5 插件方案评估

> 2026-10-07 · 基于实测与源码核对，非推断

## 一、你的方案里有个前提需要纠正

> "如果是这样的话那么 playwright 就不用打包在安装包中了"

**拆成 5 个插件并不会自动省下 playwright。** 实测体积构成：

| 组件 | 体积 | 是否在安装包内 |
|---|---|---|
| `playwright/driver/node` | **115M** | ✅ 在（Node 运行时，非浏览器） |
| `playwright/driver/package` | 13M | ✅ 在 |
| Chromium 浏览器本体 | ~170M | ❌ **不在**（用户在设置页现装） |

关键区分：安装包里的 133M 是 **JS 驱动 + Node 运行时**，不是浏览器。
用户点「安装浏览器」下载的 Chromium 从来就没进过安装包。

所以：
- 保留语雀网页登录 → 无论拆几个插件，这 133M 都在
- 想去掉 133M → 必须**彻底移除语雀网页登录**（改走 API token），代价是失去网页版能力

## 二、但你的直觉指向了一个真 bug（已修）

> "当用户选择使用语雀网页版的时候为什么还需要再额外安装一个浏览器？"

**答：不该需要。这是 bug。**

根因：`PlaywrightYuqueGateway._new_page` 调用
`launch_persistent_context()` 但**没传 `channel=`**，Playwright 默认去找
它自己下载的 Chromium，而用户的机器上只有系统 Chrome。

实测本机：
```
ms-playwright/     → 只有 ffmpeg，没有 chromium
/Applications/Google Chrome.app → 存在
默认路径（找自带）    → 失败：Executable doesn't exist
channel="chrome"     → 成功，版本 154.0.8037.98
```

**修复**：新增 `_launch_browser()`，按 `chrome → msedge → 自带 Chromium`
顺序回落。端到端实测：语雀登录状态探测正常返回，不再要求安装浏览器。

## 三、关于「用系统默认浏览器」

> "为什么还需要再额外安装一个浏览器"（隐含：应该用系统默认的）

方向对，但 macOS 上**做不到**——Playwright 不支持 Safari。

实测：
- Playwright 只支持 `chromium` / `firefox` / `webkit`，**无 safari**
- `webkit` 在本机同样需要单独下载（`webkit-2336` 不存在）
- `channel="msedge"` 在 macOS 不可用（那是 Windows 默认浏览器）

可行范围：macOS → Chrome；Windows → Chrome/Edge。Safari 需要换 WebDriver
技术栈（`safaridriver`），那是完全不同的实现，成本远大于收益。

## 四、飞书文档登录失败（已修，但有平台约束）

> "飞书文档账号点击登陆飞书文档时也显示操作失败"

**不是代码坏了，是两件事叠加：**

**① 平台硬约束**：飞书 OAuth 必须有 `app_id` 作为 `client_id`
（`exchange_user_access_token` 需要 `app_access_token`）。
飞书开放平台**没有匿名授权**。所以 `FEISHU_APP_CREDENTIALS_REQUIRED`
是合理的前置检查。

**② 真 bug —— 错误信息被吞了**：
`client-errors.ts` 没登记这个码，`clientErrorMessage` 走到 fallback：

```ts
return "操作失败，请检查设置后重试";   // ← 你看到的
```

后端明明返回了「请先保存飞书自建应用凭据（App ID:App Secret）…」，前端丢弃了。

**这不是孤例**——审计发现 **33 个平台错误码里 12 个未登记**，
全部在显示"操作失败"。已全部补齐，并加契约测试锁死。

## 五、5 插件方案评估

你的提议：飞书自建应用 / 飞书文档 / 飞书机器人 / 语雀网页 / 语雀 API = 5 个独立插件。

### 方案对比

| | A. 通道即插件（推荐） | B. 5 个独立插件包 | C. 只拆飞书/语雀 |
|---|---|---|---|
| 改动面 | 小 | 大 | 中 |
| 打包体积 | 不变 | 声称可省 133M ❌ | 不变 |
| 用户可感知的"按需下载" | 无 | 有 | 部分 |
| 引入新故障面 | 低 | **高**（动态加载） | 低 |
| 与现有注册表契合 | 完全契合 | 需重写装配 | 契合 |

### 关键判断

**A 方案（通道即插件）已经是现状。** 飞书的三种接入方式在
`FEISHU_CREDENTIAL_SPEC` 里就是三个 channel：

```python
CredentialChannelSpec(name="app",     ...)  # 自建应用
CredentialChannelSpec(name="user",    ...)  # 账号授权
CredentialChannelSpec(name="webhook", ...)  # 机器人
```

用户现在**已经可以按需配置**——不填自建应用凭据，webhook 和 user 通道照样用。
语雀同理（`web` / `api` 两通道）。

**B 方案的问题**：真正的成本不在体积，而在**运行时动态加载**。
当前后端是单体 uv runtime，插件化意味着：
- 打包时无法静态分析依赖（记忆里已有 `check_runtime_imports.py` 校验机制）
- 插件缺失时的错误处理路径全新
- 5 个插件 × 各自依赖 = 5 份冲突风险

而收益是**零**——因为 133M 在任何方案下都还在（见第一节）。

## 六、建议

**先做（已做）**：两个 bug 修复 + 错误码补齐
**待定**：
1. 语雀去掉网页登录 → 可省 133M，但要接受失去网页版能力
2. 若坚持 5 插件，需先回答：省体积的目标是否还成立？

如果目标只是"别让用户装浏览器"，**已经解决了**——不需要拆插件。
